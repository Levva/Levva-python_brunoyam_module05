# Индексы

## Как выбирали поле для индекса?

В частых запросах в местах, где используется `WHERE`, `JOIN ... ON`, `ORDER BY` условия можно проиндексировать, на больших таблицах это будет облегчать поиск. Также желательно проиндексировать внешние ключи для ускорения запросов в таблицах, связанных друг с другом.

## Если они такие удобные почем не создавать индексы на все поля сразу?

Индексы - это такие же структуры данных, которые нужно хранить и поддерживать в актуальном состоянии. Поэтому, при добавлении, удалении и изменении данных в основных таблицах, также обновляются данные во всех связанных индексах, что, на больших выборках, может существенно замедлить запись изменений. Ну и структуры данных с индексами также занимают место на диске.

## `book.id is not null` - с точки зрения индексирования, какая здесь проблема?

> Тут надо вернуться к вопросу 1.

`book.id` - это первичный ключ, занчит, для каждой записи таблицы будет всегда существовать непустой `id` с уникальным значением (так как указание `primary key` автоматически означает `NOT NULL` и `UNIQUE`), по которому можно будет найти эту запись. Поэтому условие `book.id is not null` всегда истинно: оно не отбирает ни одной строки и не нуждается в ускорении. Кроме того, для первичного ключа PostgreSQL сам создаёт уникальный индекс (`books_pkey`), так что ещё один индекс на `id` будет дублировать уже существующий, и только замедлит запись.

with SessionLocal() as session:
    try:
        stmt = update(RecordORM).where(RecordORM.id == record_id).values(
            returned_at=returned_at
        )
        session.execute(stmt)
        session.commit()
    except Exception:
        session.rollback()
        raise
